    13. Working with hql¶

    The language is half of what you use; the other half is the command and what it says back. This chapter is about the tools: the commands, the diagnostics, and the messages hql writes when a program is wrong.

    The commands¶

    Command What it does
    hql eval <program> check and evaluate a program given as an argument
    hql run <file> check and evaluate a program in a file; - reads standard input
    hql check <file> write the program's type, and the signature of every alias, without evaluating
    hql repl read, evaluate and print, keeping bindings between lines
    hql render <file> build a document from its cells (chapter 24)
    hql builtins list every step, by the provider that implements it, with its signature
    hql config the settings in force, and where each came from
    hql context [file] the execution context: the mode, the workspace, the configuration files and module roots, and where each came from
    hql doctor check the semantic-search chain and name the first missing part

    --vault <dir> names the vault, --to <format> the output format, and --envelope json wraps the answer for another program. --workspace <dir>, --bare and --context <name> set the execution context, below.

    The REPL¶

    hql repl keeps its bindings from one input to the next. The arrow keys edit a line and recall earlier inputs, from a history kept between sessions. An input goes on over several lines while a bracket is open, or while the next line opens with |, so every program in this book can be pasted in as it is written. :type asks for the type of an expression, or, given a function's name, prints the standard library's declarations of it, one per overload. :quit leaves, as do quit, exit and Ctrl-D:

    $ hql repl
hql 0.5.1. `:help` for commands, `:quit` to leave.
hql> shelf = [412, 280]
()
hql> shelf | sum
692
hql> :type shelf
List<Int>
hql> :type range
fn range(start: Int, end: Int, step: Int = 1) : List<Int>    // std/seq
hql> :quit

    What a step takes¶

    hql builtins lists every step with its signature, one line per form:

    $ hql builtins
core 0.5.0 (always available)
  size
    Collection<T> | size<T>() -> Int
    Count all element occurrences.
  contains
    Collection<T> | contains<T>(value: T (positional)) -> Bool
    Whether a value occurs in the collection.
  …

    A function of a module that the program has not imported is listed too, so the import it needs can be looked up. import lexical makes a module visible; lexical.lexical(…) names a function with its module, when two visible modules declare one name and the input does not tell them apart. The modules of lib/std/prelude.hql, string, seq, math, option, result, graph, format and io among them, are visible in every program unless the vault's hql.toml says prelude = false.

    Diagnostics¶

    A run produces a value and the diagnostics its phases wrote: warnings that change nothing, errors that make a result wrong, failures that make one impossible. Each is headed by the phase that wrote it, its severity and its kind, and names where it points, by line and column. Chapter 12 is the whole error model.

    By default hql stops at the first error. --report collect reports every error it can find:

    $ hql --report collect eval 'a = nosuchthing
b = alsomissing'
check error[unknown-name]: `nosuchthing` is not bound
 --> <expression>:1:5
  |
1 | a = nosuchthing
  |     ^^^^^^^^^^^

check error[unknown-name]: `alsomissing` is not bound
 --> <expression>:2:5
  |
2 | b = alsomissing
  |     ^^^^^^^^^^^

2 diagnostics: 0 failure, 2 error, 0 warning

    A misspelled step suggests the nearest one, and a retired name says what replaced it, on a help line under the caret:

    $ hql eval '[1, 2] | mapp(n => n)'
check error[unknown-step]: `mapp` is not a pipeline step
 --> <expression>:1:10
  |
1 | [1, 2] | mapp(n => n)
  |          ^^^^^^^^^^^^
  = help: did you mean `map`?

    A warning never changes the exit status. Names have one casing per kind — snake_case for bindings, functions and fields, PascalCase for types — and a name off its kind's convention is a warning where it is written:

    $ hql eval 'bookCount = 7
bookCount'
7
check warning[naming-convention]: `bookCount` is a binding, written in snake_case
 --> <expression>:1:1
  |
1 | bookCount = 7
  | ^^^^^^^^^
  = help: write it `book_count`

    --envelope json carries every diagnostic, whatever the level, as data, and --diagnostics-format json writes each one to standard error as one JSON document per line. A program that wants to report on itself, apart from its result, writes to a logger: the logging page of chapter 9.

    The execution context¶

    Every invocation runs in an execution context: a mode, a workspace or none, and the configuration gathered for it. The same program text checks and evaluates the same way in every mode; the context determines the documents, module roots and settings it is given.

    Modes and workspace discovery¶

    The anchor is the directory discovery starts from: the directory of the program's file for hql run, check, plan, boundary and context <file>, and the working directory for an expression or standard input. hql walks from the anchor upward and stops at the first directory holding .hmd/ or hql.toml; that directory is the workspace. The mode follows from what it holds:

    Mode Workspace Vault
    bare none none
    workspace the directory holding hql.toml none
    vault the directory holding .hmd/, with or without hql.toml the workspace

    The walk stops at the nearest boundary: a hql.toml inside a vault is a workspace of its own, and the outer vault's configuration does not reach it. The working directory is not consulted when a file is the anchor, so a program finds its workspace wherever hql is run from. A workspace marked by hql.toml alone still loads its documents as cards.

    --workspace <dir> (or --vault <dir>) names the workspace and replaces the walk; the directory must hold .hmd/ or hql.toml. --bare runs with no workspace whatever the filesystem holds, and an operation that needs a vault fails with needs a vault rather than reading the working directory as one. --bare with --workspace is a usage error. hql render discovers a workspace for each document from that document's directory, and under --bare renders none.

    hql context writes the context, each part with the layer it came from:

    $ cd ~/tmp
$ hql context ../notes/scripts/report.hql
mode:      vault
context:   work (user configuration)
workspace: /home/ada/notes (discovered from the anchor)
vault:     /home/ada/notes
anchor:    /home/ada/notes/scripts
cwd:       /home/ada/tmp
hql-home:  /home/ada/.hql (the default)
prelude:   on (the default)
config:
  /etc/hql/config.toml (system configuration, absent)
  /home/ada/.hql/config.toml (user configuration)
  /home/ada/notes/hql.toml (the workspace's hql.toml, absent)
module roots:
  /home/ada/.hql/lib (user configuration)
imports:
  none

    --envelope json writes the same as one JSON document.

    Configuration layers¶

    Bare means no workspace, not no configuration. These layers contribute in every mode, each read in turn:

    Layer Where
    system /etc/hql/config.toml on Unix, %ProgramData%\hql\config.toml on Windows; $HQL_SYSTEM_CONFIG names another file
    user config.toml in the HQL home, ~/.hql/; $HQL_HOME names another directory
    named context the selected [context.<name>] table of the system or user file
    HQL home modules ~/.hql/modules/, a module root when it exists
    workspace the workspace's hql.toml
    $HQL_PATH further module roots, separated as $PATH is
    command line --modules <dir>

    The system and user files take the keys a workspace's hql.toml takes: [modules] roots, [extensions] import and prelude, [report] mode and level, and [execution] backend. A relative path is read against the directory of the file that declares it, never the working directory. A system or user file that does not parse fails every run, naming the file.

    Module roots and extension imports gather across the layers, each once. A gathered root is a place to look, not a priority: a module that two roots provide is still an error. prelude is the last layer's that states it. The HQL home is the user's environment, not a workspace, and never a vault.

    Named contexts¶

    A named context is a [context.<name>] table of the system or user file: settings grouped under a name and reused across workspaces. It takes the keys above, and workspace, which binds a workspace, read against the directory of the declaring file. A user file's definition of a name replaces the system file's; a workspace's hql.toml defines no context.

    current-context = "work"

[modules]
roots = ["lib"]

[context.work.report]
level = "info"

[context.archive]
workspace = "../archive"

    One context is selected: --context <name>, else $HQL_CONTEXT, else current-context, else a context named default when one is defined. A selected name that no file defines fails every run, naming the layer that selected it. A context that binds a workspace replaces the walk; a context without one leaves discovery as it is. A context selected by --context or $HQL_CONTEXT that binds a workspace, together with --bare or a --workspace naming another directory, is an error; under a context selected by current-context, the command line wins.

    hql config lists and changes the selection; use-context writes current-context into the user file and keeps every other line of it:

    $ hql config get-contexts
CURRENT  NAME     WORKSPACE          DEFINED IN
         archive  /home/ada/archive  /home/ada/.hql/config.toml
*        work     -                  /home/ada/.hql/config.toml
$ hql --context archive context
mode:      vault
context:   archive (--context)
workspace: /home/ada/archive (context `archive`)
…
$ hql --context nope eval 1
hql: no context is named `nope`, which --context selects; the defined contexts are `archive`, `work`

    hql config current-context writes the persistent current-context, which --context and $HQL_CONTEXT leave unchanged, hql config use-context <name> sets it, and hql config view writes the system and user files merged, a table key by key and any other value from the user file.

    Settings¶

    The report mode and level come from the command line, then the vault's hql.toml, then the environment ($HQL_REPORT, $HQL_REPORT_LEVEL), then the selected context, the user file and the system file, then the defaults. The backend follows the same order with --backend, [execution] backend and $HQL_BACKEND. hql config says which applies, and why:

    $ hql config
report mode: strict (from the default)
report level: warning (from the default)
backend: localhost (from the default)
vault: none

    backend selects the execution strategy described in Logical steps and physical plans, and localhost is the only one. Run inside a vault, or with --vault, the last line names it and counts its cards.
